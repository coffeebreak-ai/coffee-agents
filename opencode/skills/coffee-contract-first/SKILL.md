# Coffee: протокол Contract-First

В связке Go и Python главные ошибки возникают на границах систем из-за несогласованных типов, `null`-значений и формата времени. Вместо словесного описания интерфейсов всегда проектируй строгие декларативные контракты.

## Правила проектирования контрактов
1. **Никакого кода реализации.** Не пиши бизнес-логику, хендлеры или ORM-модели. Используй только декларативные форматы:
   * Для БД — чистый **SQL DDL** (`CREATE TABLE`, индексы, `NOT NULL`, `CHECK`, внешние ключи).
   * Для синхронного API — **OpenAPI (YAML)** или **Protobuf (`.proto`)**.
   * Для очередей и стриминга (Kafka, NATS, RabbitMQ, Redis Streams) — **JSON Schema** или **Protobuf** с обязательными полями трассировки и идемпотентности.
2. **Явная типизация и nullability.** Для каждого поля явно указывай, может ли оно быть пустым (`NULL` / `optional`), значения по умолчанию и единицы измерения. Форматы не оставляй на выбор: деньги — `NUMERIC(38,18)` в Postgres или `BIGINT` в тиках, в JSON строка, не `float`; время — `timestamptz` в БД и `RFC3339` в JSON и событиях, без локальных зон; `timestamp_ms BIGINT` допустим только если весь контракт уже живёт в миллисекундах.
3. **Версионирование и совместимость.** Сразу закладывай поле версии схемы (`schema_version`) или правила эволюции (только добавление опциональных полей без удаления старых).
4. **Идемпотентность.** В каждом контракте мутирующей команды или события очереди предусматривай `idempotency_key` или `event_id` (UUID) и `created_at` в UTC. Ключ создаёт инициатор. Повторы и отмены делает только он. Получатель ключ не подменяет.
