# Coffee: протокол анализа отказов (Failure Modes)

Любой внешний вызов, запись в БД или чтение из очереди рано или поздно упадут, зависнут или придут дважды. Твоя задача — заранее спроектировать поведение системы в режиме аварии, чтобы при реализации на Go и Python не пришлось гадать, что делать при ошибке.

## Правила анализа
1. **Проверь каждый внешний стык.** Пройдись по всем стрелкам на архитектурной схеме: входящие запросы, внешние HTTP/WebSocket API, базы данных, брокеры сообщений, файловая система.
2. **Ключ идемпотентности.** В таблице укажи, кто инициатор, где хранится ключ и что считается дублем (правило владения — `coffee-contract-first`).
3. **Учитывай специфику стека:**
   * **Для Go:** таймауты контекста (`context.WithTimeout`), утечки горутин, переполнение буферизованных каналов (backpressure), обрыв WebSocket/gRPC соединений, корректный `graceful shutdown`.
   * **Для Python:** OOM при обработке батчей, блокирующий I/O и GIL, падение синхронных воркеров (Celery), медленный холодный старт; для CPU — внешний многопоточный оркестратор, а не потоки Python.
4. **Никаких общих фраз.** Вместо «обработать ошибку и залогировать» пиши конкретику: *«3 ретрая с exponential backoff (100ms, 500ms, 2s) + jitter, при исчерпании — отправка в DLQ `orders.dlq` и инкремент метрики `order_process_errors_total`»*.

## Обязательный формат вывода в ТЗ
Оформляй результат в виде единой таблицы:

| Компонент / Стык | Сценарий отказа (Failure Mode) | Как детектируем (Метрика / Алерт / Код) | Реакция системы и восстановление (Retries, DLQ, Fallback, Idempotency) | Влияние на пользователя / данные |
| :--- | :--- | :--- | :--- | :--- |
| *Пример: Внешний API биржи* | *HTTP 429 (Rate Limit) или таймаут > 2с* | *Метрика `exchange_http_errors_total{code="429"}`, таймаут контекста* | *Circuit Breaker (открывается после 5 ошибок), пауза по заголовку `Retry-After`, запрос ставится в локальную очередь с лимитом* | *Задержка обновления данных до 5с, данные не теряются* |
