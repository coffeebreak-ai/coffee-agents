# Coffee: разработка на Python

При написании кода на Python придерживайся современных стандартов (Python 3.11+) и правил ниже.

## 1. Типизация и валидация данных
* Обязательно используй аннотации типов (type hints) для всех аргументов функций, возвращаемых значений и атрибутов классов.
* Избегай `Any`, где можно описать структуру через `TypedDict`, `dataclass` или `Pydantic` (`BaseModel`).
* Все данные на границах системы (входящие API-запросы, сообщения из очередей, ответы внешних сервисов, конфиги) валидируй через схемы/модели строго по контракту из ТЗ.

## 2. Асинхронность и производительность
* В `asyncio`-приложениях строго запрещены блокирующие вызовы внутри event loop (`time.sleep`, синхронный `requests`, тяжелый CPU-bound парсинг без `asyncio.to_thread` или выноса в процесс).
* Управляй внешними соединениями (HTTP-клиенты, пулы БД) только через асинхронные контекстные менеджеры (`async with`), не создавай новую сессию на каждый запрос.
* Используй `asyncio.TaskGroup` (или явный контроль фоновых задач с сохранением ссылок), чтобы исключения в фоновых задачах не терялись молча.

## 3. Обработка ошибок и ресурсы
* Никогда не пиши голый `except:` или глушение `except Exception: pass`. Лови конкретные типы исключений.
* Логируй ошибки с полным трейсбеком (`logger.exception(...)`) и структурным контекстом (ID сущности, ключ идемпотентности).
* Для финансовых, торговых и точных расчетов используй `decimal.Decimal`, а не `float`.

## 4. Архитектура и стиль
* Разделяй транспортный слой (роуты, консьюмеры очередей), бизнес-логику (сервисы) и слой работы с данными (репозитории). Бизнес-логика не должна зависеть от HTTP-фреймворка.
* Не хардкодь секреты, URL и таймауты — выноси их в настройки/конфиг проекта.

## 5. Проверка перед завершением
* Временный тест на `pytest` допустим, чтобы проверить гипотезу или найти решение. До сдачи файл удали: `test_*.py` в diff не остаётся.
* Проверь код инструментами, принятыми в проекте: `ruff` обязателен, `mypy`/`pyright` если настроены. Конфиги линтеров не правь.
